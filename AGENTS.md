# AGENTS.md

Guide for coding agents and contributors working on PRism. Product context lives in [PLAN.md](PLAN.md). User-facing setup lives in [README.md](README.md).

## Architecture

Electron app, three processes plus shared code:

### Data model

SQLite at `~/Library/Application Support/PRism/prism.db`. Tables: `settings`, `skill_sources`, `repos`, `skills`, `stage_bindings`, `prs`, `pr_flags`, `snapshots`, `activity`, `review_latency`, `runs`, `run_events`, `findings`, `asks`, `post_gates`.

### Agent runs

- Lifecycle: `queued → preparing → running ⇄ needs_you → done | failed | cancelled`. The Agent SDK `session_id` is stored per run; answers and app restarts resume the same session.
- `prism_ask_user` records an ask and sets the run to `needs_you`; the agent ends its turn, and the answer is sent as the next prompt with `resume`. One question can be open at a time, and Stop closes it.
- A run that ends without its report tool gets one nudge, then fails. While a stopped run winds down, follow-ups and new runs on its pull request are refused.
- A run loads its skill by id, so rebinding a stage does not change runs already started; a run whose skill was deleted fails.
- Board: one review loop on both tabs (PLAN.md §6). Action columns (Reviewing, Addressing on My PRs, Approved) start something on drop; state columns (Waiting review on My PRs / To review on Reviews, Changes requested, To re-review, To approve, Done) are derived. A card's stage is the run overlay, else a manual move, else the loop stage (`loopStage`: the last closed review or address gate, or replies gate on My PRs (address and replies hand the card back to Waiting review until someone else requests changes after the post, `prs.changes_requested_at`), an approval from PRism at the current head; a NO GO / GO WITH NITS moves to To re-review only once the head moves past the head stored when it was posted, `post_gates.posted_head_oid`), else the GitHub stage (`deriveStage`). Run overlay: an active or finished-but-unposted review run shows in Reviewing (until posted, skipped, my next GitHub review, a manual move or Dismiss), address runs in Addressing, and any `needs_you` run in the Needs you column (shown only when non-empty). A finished verdict stays visible while another stage (test plan, draft replies) runs, and is flagged `stale` when the PR head moved since. Dismiss hides that run and earlier failed or cancelled runs; dismissing a run that finished without error also hides earlier finished runs of the same kind (review and re-review, address, test plan, draft replies).
- Sync keeps a pull request that has any undismissed run (active or finished), even when it no longer involves the user. Removing a repository or resetting stops its runs first.
- Auto-run (`autorun.ts`, a per-repository switch, off by default): only a review request that names you starts a run: when it appears, when it is re-requested after your review, or when it names you after a team request. It runs Review, or Re-review when you reviewed the pull request before (`reviewStageFor`), with a transcript note saying it started automatically. New commits and team requests never start a run. A request waits in the `autoRunQueue` setting while 2 runs are queued, preparing or running (`needs_you` does not count), and is dropped when it no longer applies: auto-run turned off, no longer requested, closed, hidden, archived, in Reviewing (a run or unposted results), or a run started on it since the request. A request whose run fails to start (a stopped run still winding down, the runner not ready) stays queued for the next sync, up to 3 tries, at most one per sync.
- Any stage can be started from the drawer (stage picker) or the card menu; a drop on an action column starts its stage (`columnStage`: Reviewing runs re-review once I reviewed on GitHub or a review run finished, else review; Addressing runs address), and `runStageFor` picks the drawer's default. `runStagesByTab` lists the stages offered per tab. `nextSteps` gives a card in a state column its main next step, a `secondary` one shown beside it (Address next to Post GO on my pull request in To approve when it has unresolved comments, e.g. the nits of a GO WITH NITS), and the other runs, Approve and state columns; `NextStepButton` (`board/next-step.tsx`) shows them in the drawer header and in a closed gate's summary.
- Re-review runs get the pull request's open findings from earlier review and re-review runs, and a scope computed by PRism (`computeDelta` against the last finished review): only the new commits (and, after a force-push, the reviewed commits it removed; a removed commit whose subject matches a new one counts as rewritten), nothing new (prior-findings pass only, with a hint to check base-merge conflict resolutions) after base merges or a pure rebase, or the whole pull request when the old head is gone. The scope is noted in the transcript. A review run on an already reviewed pull request is shown as **Full review**: it reads everything but gets the open findings as a do-not-repeat list.
- `prism_report_findings` is refused, with nothing recorded, once the run's review is posted (a follow-up answers in text instead, so the posted findings keep their GitHub comment ids).
- `prism_report_findings` is refused, with nothing recorded, when a finding's line is not in the pull request diff (`git diff <reviewed base>...<reviewed head>` in the worktree, `parseUnifiedDiff`); the error lists the lines and how to fix them, so the agent reports again with lines GitHub can anchor.
- Repeat guard: every reported finding gets a `hunk_hash` anchor; a review or re-review finding that matches an open earlier finding (its `priorFindingId`, or the same path and normalized title plus the same anchor, a line within 3 of the earlier one, or no line on either side; a different title on the same code is kept) is dropped before it is stored, noted in the transcript and named in the tool reply.
- Address and draft-replies runs take review threads: the picker passes `threadIds`, otherwise the runner selects every unresolved thread that is not already answered (`needsAnswer`: its last comment is not a reply of yours) at start, and the picker ticks the same ones. Address runs also get the open findings that PRism posted in a review body (no inline thread: `bodyFindings`, findings whose `gh_comment_id` is their gate's review id); they are stored on the run (`findings_json`), listed in the prompt under keys `finding:<id>`, reported in `prism_report_changes` with that key as `threadId`, count for the gate's verdict check and get no reply. An address run with no thread and no such finding, or a draft-replies run with no thread, fails before the agent starts. The ids are stored on the run (`threads_json`) and listed in the prompt; agents use them as `threadId` in `prism_report_changes` / `prism_draft_replies`. Threads are paged, with the last 30 comments of each.
- A finished run with a session can be continued with a follow-up message (`runs:followUp`, same session, un-dismisses the run; from the Runs tab or Ask agent anything on its step in the Actions tab, which then opens the Runs tab) or resumed by the user in a terminal (`claude --resume`, outside PRism's tool guard and push block; the pre-push hook still applies in PRism worktrees).
- Cost and tokens are session totals from the SDK (`total_cost_usd`, `modelUsage`), which continue across `resume`; a run stores the latest total of its session.
- IPC: `runs:*`, `prs:threads`, `apps:*` channels; events `runs:changed` (a `Run`) and `runs:event` (a transcript `RunEvent`).

### Notifications, Dock badge and menu bar (`desktop/`)

- Kinds, each with a switch in Settings → Notifications: an agent question (answer from the notification: type a reply or pick one of its options, sent like `runs:answer`), a run that finishes (ready to post, with the verdict and the findings count) or fails, a review request, failing checks on my pull request. Run notices come from status changes seen in this app session (`runNotice`), pull request notices from sync events (`prEvents`).
- Nothing is shown while a PRism window is focused or for hidden and archived pull requests. A review request or a CI failure on the same head is not repeated within 30 minutes. A question's notification is removed once its run leaves Needs you.
- The Dock badge and the menu bar count agent questions and runs ready to post (`agentNeedsYou`: a `needs_you` run, or a finished review or address run whose gate is open; hidden and archived excluded). This is narrower than the sidebar's needs-me counts.
- Menu bar: a template icon (`resources/tray/`, bundled via `extraResources`) with that count and a native menu: Needs you (the counted items), Your turn (the other cards the sidebar counts, `isNeedsMe`: To review, To re-review, To approve, Changes requested on My PRs; not counted), Running, Open PRism, Sync now, Quit. Items and notifications open the pull request's drawer on the matching board and tab (`OpenTarget`).
- Permission: macOS asks once per app, on its first notification, and after a refusal only System Settings can turn it back on. Electron cannot read that setting, so onboarding has a Notifications step whose Turn on notifications button sends a test (the macOS prompt shows while the user is looking), and Settings → Notifications has Open System Settings next to Send a test.
- IPC: `settings:getNotifications`, `settings:setNotifications` (a partial patch), `notifications:test` (bypasses the settings and the focus check), `notifications:openSettings` (opens System Settings → Notifications), `app:pendingOpen`; event `app:openPr`.

### Post gate (`actions.ts`)

- A finished review or re-review run gets a review gate, an address run an address gate, a draft-replies run a replies gate (`gateKindOf`). The gate row (`post_gates`) is created on first read and stores only the user's choices; `gates:get` recomputes the checklist live (GitHub head, pending review, own PR, worktree status, diff).
- Post mode: `settings:getPostMode` (global, default `draft` = Stage as pending draft), overridden per repository (`repos.post_mode`, `repos:setPostMode`) and per gate.
- Review: findings are included/excluded and edited (`findings:update`, refused once posted), then confirmed in one click. Findings on a commentable diff line (from `compare/<reviewed base>...<reviewed head>`) become inline comments; the rest go in the review body under "Other findings". The review status is pre-filled from the verdict and clamped to Comment on your own pull request, where the Actions tab hides the status picker. If you already have a pending review, PRism adds threads to it (and submits or updates its body, with a single AI tag at the end) instead of starting a second one. Posted comment ids are stored on findings (`gh_comment_id`). The staged or submitted body is stored (`post_gates.posted_body`); after a pending draft the Actions tab shows it with a Copy button, because GitHub does not prefill it when you submit the draft.
- Address: threads need a verdict, Commit runs `git add -A` + `git commit -m` in the run's worktree, Push runs `git push --force-with-lease=refs/heads/<branch>:<last verified push, else head at checkout> <remote> HEAD:refs/heads/<branch>` with a one-time `PRISM_PUSH_NONCE` (written to `<userData>/hooks/.push-nonce`, removed after, one push at a time) and then polls GitHub until the PR head equals the local head. The push target is stored on the run at checkout (`push_remote`, `push_ref`).
- Replies: only ticked threads are answered; every posted reply and review body ends with `aiTag`; an AI signature the agent added itself (an italic or 🤖 last paragraph naming AI or Claude, as some skills ask for) is stripped when replies are recorded and again when posting (`withAiTag`), and the contract tells agents not to sign. Replies already posted keep their URL, so a retry after a failure posts the rest.
- Commit, push and post are refused while any agent run is active on the pull request, and one action (commit, push, post, skip, approve) runs per pull request at a time. Posting or skipping closes the gate, stores its mode and status, clears a manual stage and moves the card per `reviewDirection` (the gate's `nextStage`, shown on the Post button). Approve (`gates:approve`, a drop on Approved) submits an Approve review saying GO (a Comment on your own pull request, adding to your pending review if any) and stores `pr_flags.approved_oid`.
- Guardrails (PLAN.md §3):
  - Layer 1: `canUseTool` + `PreToolUse` hook (`guard.ts`) check every tool input that has a `command`, once per tool use. git is an allowlist by subcommand (read commands everywhere; address runs can also add, rm, mv, apply and unstage), `-c` takes only an allowlist of display keys, `GIT_*` variables other than `GIT_PAGER`, `GIT_TERMINAL_PROMPT` and `GIT_OPTIONAL_LOCKS` are refused, options that skip hooks or run other programs (`--no-verify`, `--upload-pack`, `--exec-path`) are refused, long options are matched as git does (exact name first, then unique prefix), `git-<sub>` programs run by name or from a `git-core` folder, and git's server programs like `git-receive-pack`, are checked as `git <sub>`, and `git fetch` may only write `refs/remotes/` and `refs/tags/`. `npm`, `pnpm`, `yarn` and `bun pm` `version` commands commit and tag, so they need `--no-git-tag-version` (npm abbreviations like `npm vers` and options before the command are covered). `gh` is read-only, with `gh api` parsed flag by flag. Dynamic commands (`$(…)`, a variable as the command or as a variable name, `eval`, a shell reading stdin) are refused, `$(…)` and backticks are checked recursively, heredoc bodies only for substitutions (not at all with a quoted delimiter), and `case` patterns and `[[ … ]]` operands are read as patterns. Syntax the guard cannot model is refused rather than parsed, with a hint on how to rewrite the command: lone `{`/`}` and `(` outside command start, zsh `<n-m>` globs, carriage returns, heredocs inside `$(…)`, `case` patterns with line continuations, no closing `)` or starting with `esac`, `${ …; }` command substitutions (also `${|…}`, `${<…}` and `${>…}`), attached shell options like `-oerrexit`, the zsh `braceccl` and `globsubst` options, `&>` in sh/dash/ksh scripts and `[[ … ]]` or `(( … ))` commands in sh/dash scripts (read from the lexed script, so quoted text like `[[:space:]]` passes, and the user's functions and aliases keep bash/zsh rules), csh/tcsh/fish, writes to command tables (`functions`, `commands`, `aliases`, `BASH_CMDS`…), `functions -c`/`-M`, `autoload`, `exec -c`, `npm_config_*`, `LESS*`, and `PAGER`/`GH_PAGER`/`MANPAGER` values other than plain pagers. Scripts passed to `sh -c` and `npm -c`/`--call` are checked as commands. The `git commit`/`git push` text backstop applies to unquoted words, interpreter code, shell `-c` scripts and user function bodies. Commands over 64 KB are refused (long content goes in a file, written with the Write tool in stages that can edit), and a work budget keeps every check fast. The user's shell aliases are expanded and the user's shell functions are checked through their bodies (probed once per app session, see `system/shell.ts`). Edits must resolve, through `..` and symlinks, to a path inside the worktree; read-only stages cannot edit.
  - Layer 2: the same `gh` policy as a shim in `<userData>/bin`, first on the agent `PATH`.
  - Layer 3: a per-worktree `core.hooksPath` pre-push hook that needs `PRISM_PUSH_NONCE` to match `<userData>/hooks/.push-nonce`, plus a push block in the agent env (`GIT_CONFIG_*` setting `url.prism-push-blocked://.pushInsteadOf`, with an exact entry per configured remote URL of the clone, read before `insteadOf` rewriting, so longer user rules can't win) that `--no-verify` cannot skip. A remote it can't cover, such as one with its own `pushurl`, is named in the run's transcript.
  - Layer 5: `prismContract` appended to the system prompt.
  - Project settings, hooks and `.mcp.json` come from the user's clone (`projectConfigRoot`), never from the pull request checkout. Only PRism's MCP server is loaded (`strictMcpConfig`), and the built-in `AskUserQuestion` is disabled in favour of `prism_ask_user`. Tool output, findings, questions and errors are redacted before they are stored.
  - These layers stop accidents and naive prompt injection, not a determined agent: Bash can still run scripts or read local credentials. An OS-level sandbox is a follow-up.
- The adapter uses the user's installed `claude` binary (`pathToClaudeCodeExecutable`).

## Conventions

- **IPC:** add a channel to `ipcChannels` in `src/shared/channels.ts` and its zod `input`/`output` in `ipcContract` (`src/shared/ipc.ts`), then a handler in `src/main/ipc/`. Events go in `ipcEvents` + `IpcEventPayloads`. Validate everything crossing the boundary with zod.
- **Schema:** edit `src/main/db/schema.ts`, then `pnpm db:generate`. Commit the generated SQL and snapshot.
- **Services** take `ctx: Ctx` first and stay free of Electron imports where possible so they are testable.
- **Tests:** Vitest. Services are tested with an in-memory DB (`openDb(':memory:', migrations)`) and fakes (e.g. a fake `GithubApi`; implement `graphqlPartial` and `get` in fakes).
- **Comments:** minimal, default none. Name things well instead.
- **UX:** no Save buttons for simple choices (selecting saves), custom pickers over native controls, one-click actions, end flows with a summary.
- **Public repo:** generic names only in code, docs, tests and commits (`acme`, `octocat`, `mattpocock/skills`). No private repo names, internal tools or personal data.

Agents run by PRism, and agents working on this repo, never commit, push, or post on GitHub on their own. In the app, only `ActionService` (`services/actions.ts`) commits, pushes and posts, after the user clicks the matching button in the post gate. Guardrails: PLAN.md §3.

## Gotchas

- The preload allowlist is not hot-reloaded in `pnpm dev`: restart the app after adding a channel or event, else "Unknown channel".
- Subscribe to board events (`prs:changed`, `sync:status`) in `RootLayout`, not `AppLayout`: onboarding sits outside `AppLayout`.
- Electron drag regions (`drag` utility) ignore z-index: anything clickable that overlays one (drawers, dialogs) needs `no-drag`, or clicks on it start a window drag.
- dnd-kit's default auto-scroll threshold jerks the wide board sideways; keep `threshold.x` around `0.08`.
- Escape closes the drawer except while a text field has focus, so a half-written follow-up or finding edit is not lost (`onEscapeKeyDown` in `drawer.tsx`).
- The board's horizontal scroller clips anything drawn outside a column, so column highlights stay inside it (the drop ring is `ring-inset`).
- A card's draggable body (`role="button"`, keyboard drag, accessible name) is separate from its run strip and answer form, which stop pointer and key events. Keep interactive controls out of the body. Column visibility is frozen while a drag is in progress.
- Manual stage moves are refused while the card has a live run, in the UI and in `setPrStage`.
- GitHub GraphQL returns `data` with `errors` on partial failures. Use `graphqlPartial` when null nodes matter (e.g. `nodes(ids:)`), and only drop a PR on `NOT_FOUND`.
- In `pnpm dev` macOS shows the Electron bundle's name (the Dock uses its file name), so `postinstall` runs `scripts/dev-app-name.mjs`: it renames `node_modules/electron/dist/Electron.app` to `<productName>.app`, points `node_modules/electron/path.txt` at it, sets `CFBundleName`, re-signs it ad hoc and re-registers it with LaunchServices. Scripts that launch the dev binary should use `require('electron')` rather than a hard-coded `Electron.app` path. Run the script again by hand after reinstalling Electron.
- Local builds must be ad-hoc signed (`pnpm install:app`). Signing with an Apple Development cert + hardened runtime makes the app die on launch.
- Release builds (`pnpm dist:mac`) are signed with a Developer ID Application certificate, whose private key must be in the login keychain. Apple Development and Apple Distribution certificates do not work for an app shared outside the Mac App Store, and only the Apple developer team's Account Holder can create a Developer ID certificate (Xcode otherwise fails with "This operation can only be performed by the Account Holder"). electron-builder notarizes when `APPLE_KEYCHAIN_PROFILE` (a `xcrun notarytool store-credentials` profile), `APPLE_ID` + `APPLE_APP_SPECIFIC_PASSWORD` + `APPLE_TEAM_ID`, or `APPLE_API_KEY` + `APPLE_API_KEY_ID` + `APPLE_API_ISSUER` is set, and skips it with a warning otherwise.
- Notifications go through macOS UserNotifications, which needs a signed bundle. The ad-hoc signature from `scripts/dev-app-name.mjs` or `pnpm install:app` is enough for macOS to ask to allow PRism on the first notification (or Settings → Notifications → Send a test); nothing shows until you allow it. Electron still emits `show` when macOS drops the notification, so check `log show --last 5m --predicate 'process == "NotificationCenter"'` for `notificationsAllowed: false`. The dev bundle's id is `com.github.Electron`, shared with every Electron dev app, so a choice made for another one applies to PRism in `pnpm dev`. Electron's `Notification` objects are kept in a map so their click and reply handlers survive garbage collection.
- better-sqlite3 ships N-API prebuilds, so the same binary works in Vitest and Electron.
- TypeScript 7: no `baseUrl`; `paths` must start with `./`.
- oxlint flags `no-shadow` (watch `resolve` in tests). `__typename` is allowed.
- Visual checks: `pnpm build`, then Playwright `_electron` with `--user-data-dir=<scratch dir>` for a fresh profile.
- The Agent SDK is ESM-only; main loads it with a dynamic `import()` (kept as-is in the CJS bundle).
- Bare `allowedTools` entries bypass `canUseTool`; keep guards in the `PreToolUse` hook too, since project settings can also allow tools.
- The pre-push guard enables `extensions.worktreeConfig` on the clone and sets `core.hooksPath` per worktree, so the repo's own hooks do not run in PRism-created worktrees. Reused worktrees (created by other tools) don't get the hook; PRism still fast-forwards them, and follows force-pushes when they are clean at the head it last checked out. `git push --no-verify` skips hooks, which is why the push block lives in the agent env. PRism re-installs the guard when it reuses its own `pr-<n>` worktree.
- The CLI snapshots the user's `~/.zshrc` (or `~/.bashrc`, `~/.profile`) and loads its aliases and functions before every Bash command, so they run in agent shells; `ZDOTDIR` does not change that. The snapshot keeps the first 1000 alias lines, turns global aliases into regular ones and skips functions named `_x…`. PRism probes them the same way once per app session (`probeShell`, in the shell the CLI uses: `CLAUDE_CODE_SHELL` or `SHELL` when it is zsh or bash, else `/bin/zsh`), so restart PRism after editing them. A probe that fails or times out is noted in the run's transcript and retried on the next run.
- Never let the SDK read project config from a pull request checkout: a PR can ship `.claude/settings.json` hooks that run as soon as a session starts. Pass `projectConfigRoot` (the user's clone).
- SDK result messages carry session totals (`total_cost_usd`, `modelUsage`) that continue across `resume`. Store the latest value; summing segments double-counts.
- Test agent runs with a fake `AgentAdapter` and a fake `prepare` (see `runner.test.ts`); `worktrees.test.ts` uses real temp git repos.
- `vitest.setup.mts` drops git settings the test run inherits (`GIT_CONFIG_*`, `GIT_DIR` and the like), so the git push tests also pass inside a PRism agent run, whose push block rewrites every push, and inside git hooks.
